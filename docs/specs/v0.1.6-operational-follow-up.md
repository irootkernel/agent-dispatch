# v0.1.6 Operational Reliability Follow-up

> **Status:** Approved planned baseline
> **Decision:** D-027
> **Release target:** v0.1.6
> **Shipped baseline:** v0.1.5
> **Roadmap owners:** E14 through E17

## 1. Purpose

This specification adopts the focused follow-up discovered while deploying
Agent Dispatch v0.1.5 against Hermes Agent v0.20.5 on macOS/arm64. The release
closes exactly three operational gaps:

1. guided Wiki setup must select and preserve one route and be safely rerunnable;
2. Hermes 0.20.5 and later must remain compatible without `--mutex-key` under
   an explicit local serialization guarantee;
3. durable notification work must make bounded progress without a remembered
   manual drain command.

The separately requested general `make verify` remediation is not part of this
release. Hermes core, private state, plugins, versions, and tags remain outside
Agent Dispatch authority.

## 2. Guided Setup Contract

`setup wiki` accepts `--route <id>`. A one-route configuration may select its
only route automatically. A configuration with multiple routes must use the
flag or an interactive, clearly rendered choice; non-interactive execution
without a choice fails. Every route-scoped nested command, printed Watchman
command, baseline operation, and final enable command uses that exact route ID.

The setup baseline is the public command:

```text
agent-dispatch reconcile --route <id> --reason initial --baseline-only
```

Baseline-only reconciliation is permitted only when configuration and runtime
activation are disabled. It enumerates the bounded resource snapshot and
atomically records the snapshot plus a route baseline record. It creates no
policy decision, dispatch intent, Hermes task, completion notification, or
production acknowledgement. It cannot submit and cannot be used to resolve an
active, uncertain, quarantined, or production-enabled route. A crash leaves
either the previous baseline or the complete new baseline; rerunning converges
without duplicate work.

The final setup summary reports separately:

- configuration enabled state;
- runtime activation state;
- Watchman binding state;
- initial baseline state;
- production acknowledgement state.

It prints the exact reviewed `route enable` command and never executes it.

## 3. Hermes Mutex Compatibility and Serialization

Hermes 0.20.5 is the minimum supported release. Later releases remain
probe-eligible with no fixed maximum, but only when their public shapes pass the
same bounded capability probe. `--mutex-key` is optional defense-in-depth
capability evidence. Probe, capabilities, preflight, enablement, rendering,
submit-time executable revalidation, and status use one of these effective
modes:

- `agent-dispatch-group-enforced`;
- `agent-dispatch-group-plus-target-mutex`;
- `unsupported-unsafe`.

Every destination has an effective Agent Dispatch serialization group. The
planned resolution order is explicit `serialization_group`, existing
`mutex_key` as a deprecated compatibility alias, then a resource-derived group.
The default is exactly `resource:<resource_id>`, where `resource_id` is the
unchanged `resources` map key. Explicit group values are 1 through 255 ASCII
bytes matching `[A-Za-z0-9][A-Za-z0-9._:/-]*`; they receive no case folding or
Unicode normalization. An explicit default-form value intentionally joins the
resource-derived group. `serialization_group` and `mutex_key` may coexist only
when their values are identical, in which case validation emits a deprecation
warning. Different values fail validation. New configuration never emits
`mutex_key`.

A group is global within one Agent Dispatch SQLite state database. At most one
active child may hold it. New relevant work for an occupied group merges into
the selected destination lane's dirty generation. Completion promotes the
waiting lane with the oldest first-dirty sequence, breaking ties by destination
ID; retry retains the slot and rerun transfers it atomically. Independent groups
may run concurrently.

Destinations governing the same resource but using different groups fail
preflight unless every involved route sets
`allow_cross_group_concurrency: true`. This acknowledgement and each effective
group participate in destination and route revision, so every topology change
requires production re-acknowledgement. Agent Dispatch never claims global
single-writer safety across different state databases.

When target mutex support is absent the renderer never emits `--mutex-key`.
When a later eligible Hermes exposes the flag, the renderer sends the effective
serialization group as a complementary target mutex; it never replaces the
local group slot. The product floor is exactly 0.20.5. An omitted configured
floor, a configured floor below 0.20.5, or an installed version below the
configured floor fails before side effects and is never rewritten implicitly.
The atomic `hermes set-minimum-version <target> <version>` helper accepts only
versions at or above 0.20.5, updates only the selected target floor, validates
and replaces the configuration, and leaves every affected route revision-paused
for probe, preflight, and explicit production re-acknowledgement. A configured
higher floor is permitted; there is no product maximum, and capability probing
still decides compatibility after version eligibility.

E15-T4 removes every exact previous-baseline reference from current tracked
files, including historical documents, fixtures, and release notes. This is an
implementation deliverable; Git history and existing tags are not rewritten.

The schema migration is additive and configuration-independent. The first
topology reconciliation materializes group membership from current
configuration. If several preserved active children resolve to one group, all
historical identities remain intact, the group reports
`serialization_conflict`, and new acquisition, promotion, retry, and rerun are
blocked. No representative holder is selected. Existing `work begin`, `work
complete`, and `work fail` transitions, read-only inspection, status, doctor,
and existing safe explicit recovery exits remain available. When one active
child remains it atomically becomes the holder; when none remains the same
transaction promotes the oldest first-dirty lane. Every conflict, blocked
operation, and resolution records typed evidence and an audit row.

## 4. Automatic Notification Drain Contract

The planned per-route configuration is:

```yaml
notifications:
  events: []
  sinks:
    - id: ops-log
      type: log
  drain:
    mode: after-command
    limit: 100
    failure_policy: preserve-pending
    pending_warn_after: 1h
    retry:
      initial_backoff: 30s
      max_backoff: 15m
      multiplier: 2.0
      jitter_fraction: 0.2
```

An omitted drain block on an existing v0.1.5 configuration means `manual`.
Newly generated Wiki configuration uses `after-command`. Supported modes are:

- `manual`: only an explicit notification drain delivers pending records;
- `after-command`: one route-scoped pass bounded by the configured item limit
  and a non-configurable ten-second automatic wall-clock budget runs after a
  successful notification-producing state transition commits; a managed
  fifteen-minute launchd recovery schedule is required before production
  enablement;
- `scheduled`: ordinary commands do not auto-drain and a generated launchd
  recipe chains drain after a healthy scheduled reconciliation.

Automatic delivery is never part of the source transaction. Failure cannot
roll back or relabel source state, change successful command exit status,
resubmit work, or create a recursive notification about a successful drain.
Ambiguous and retryable outcomes remain pending under the original stable
idempotency identity; refused delivery remains inspectable and explicitly
retryable. Ambiguous and retryable outcomes persist their next-attempt time.
The retry delay starts at 30 seconds, doubles to a 15-minute cap, applies 0.2
jitter symmetrically over plus or minus 20 percent once per retry, and persists
the resulting deadline so every process observes the same due time. Migrated
pending notifications are immediately due. Automatic drain and explicit
`notifications drain` both select due work only. `notifications retry <id>` is
the sole operator bypass: it returns an ambiguous, retryable, or refused record
to pending and makes it immediately due. Concurrent drainers atomically lease
disjoint due work. Every claim carries a fencing token; a worker that loses its
claim cannot record an outcome after another worker recovers it. Lease expiry is
the effective delivery deadline plus a thirty-second margin. A crash after
source commit or after remote delivery leaves recoverable at-least-once work.

`schedule render|install|inspect|disable|uninstall --route <id> --platform
launchd` resolves the actual binary and configuration paths. The managed label
and plist path derive from the instance ID, route ID, and a digest of the
configuration absolute path. The plist invokes one internal `schedule run`
command directly, never a shell chain. In after-command recovery mode that
command performs due-only drain; in scheduled mode it drains only after a zero
`reconcile --submit` result. After-command recovery runs every fifteen minutes.
Scheduled mode runs daily at 03:00 local time by default (`--at HH:MM`
overrides it).

Install is idempotent for an identical definition and refuses to overwrite a
different definition. Inspect checks plist presence, loaded state, and the
rendered-definition digest. Disable unloads while preserving the plist;
uninstall unloads and removes only that exact managed plist. Configuration,
logs, SQLite state, and notification history remain. Schedule logs rotate at
10 MiB per file with the latest three files retained. Setup prints but never
runs the exact install command. Preflight and production enablement require an
installed, loaded, definition-matching schedule for automatic modes.

The after-command registry includes dispatch, work completion/failure,
applicable dispatch retry/rerun, quarantine resolution, reconciliation, and
drift evaluation. Setup, baseline-only and read-only commands, and explicit
notification drain are excluded. After a registered command exits successfully
and its core transaction has committed, it drains existing due work for every
affected after-command route even if that invocation created no new
notification. A failed core command never auto-drains; the fallback owns any
already committed notification.

The ten-second wall budget applies to the entire CLI invocation, not per route.
Multiple affected routes are visited in route-ID order and one notification per
route per round prevents one route from consuming the item budget. At expiry,
unstarted claims are released; started delivery receives context cancellation
and either records a fenced outcome or remains lease-recoverable. A successful
automatic pass is silent; problems write bounded diagnostics to stderr only.
The core command's original stdout or JSON and successful exit status are
unchanged.

Status and doctor expose pending count and age, due/backoff counts, live and
expired claims, the latest drain evidence,
mode and limit, scheduler expectation/evidence/overdue state, repeated
ambiguous or retryable outcomes, and unresolvable sinks. No notification
payload or diagnostic may include document bodies, front matter, secrets, or
an unredacted endpoint.

## 5. Compatibility, Migration, and Rollback

Configuration remains `version: 1` with additive fields and explicit effective
defaults. Serialization and drain behavior join route/destination revisions.
Drain behavior also has an inspectable drain-policy revision but does not join
the notification-policy revision used by notification identity, so existing
notification IDs and idempotency keys remain stable. Capability evidence
advances to a new probe-contract version and old evidence becomes stale with a
re-probe remediation.

SQLite migrations are forward-only. Existing dispatch, receipt, lane, and
notification identities remain unchanged. Upgrade instructions require a
verified pre-migration backup, capability re-probe, preflight, and explicit
production re-acknowledgement where a serialization revision changed.
Downgrade restores the pre-upgrade database, previous binary, and compatible
configuration together; no down migration is provided.

## 6. Required Delivery Evidence

E17 cannot release v0.1.6 until the repository records:

1. concise design and changed-contract summaries;
2. exact migration and CLI/config examples;
3. acceptance-test mapping and focused command results;
4. clean-host setup and post-Watchman-install rerun transcripts;
5. real Hermes v0.20.5 probe and preflight evidence;
6. shared-group and independent-group concurrency demonstrations;
7. completion, outbox commit, automatic delivery, and timeout retry evidence;
8. known limitations plus upgrade and rollback instructions;
9. full repository verification and two reproducible darwin/arm64 builds.

All real-environment evidence uses disposable state, vaults, boards, and
profiles. No production route is enabled and no production Hermes task is
created by the validation setup flow.
