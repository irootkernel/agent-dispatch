## D-001 - 2026-08-19 - Logical request payload has a single source of truth

**Decision.** `docs/02-contracts/hermes-task-contract.md` §2 is the only specification of the logical Hermes task request. The previously duplicated `TaskRequest` field list in `docs/01-architecture/hermes-integration.md` §5 was removed and now references the contract. A schema was added (`schemas/hermes-task-request.schema.json`), and `schemas/dispatch-intent.schema.json` now constrains `request` with a `$ref` to it. The dispatch intent stores the request verbatim; envelope fields (`dispatch_id`, `route`, `generation`, `idempotency_key`, `content_fingerprint`) are deliberately duplicated inside `request` so the record is self-contained for audit.

**Context.** Review found the same logical request described twice with different field shapes (`route_id` vs `route.id`, `resolved_workspace` vs `resource.workspace`), while the persisted `request` field was unconstrained (`"type": "object"`).

**Consequences.** The nested contract form wins; title, trusted instructions, and receipt instructions remain adapter-rendered templates, not payload fields. Two examples were added (`examples/dispatch-intent.json`, `examples/dispatch-receipt.json`) so every schema has a validating example.

## D-002 - 2026-08-19 - Error category enumerates the exit-code classes

**Decision.** `docs/02-contracts/error-model.md` now defines `category` as exactly one value per nonzero exit-code class (13 values, 1:1 with exit codes). The stable error code registry is closed for v0.1 and maps every code to a category and exit code, including the five adapter-defined codes (`source_unsupported_version`, `source_missing_required_metadata`, `source_position_unusable`, `source_unsafe_path`, `capability_unsupported`). Exit code 1 is unassigned and must never be emitted; the CLI entry point must recover panics and exit 40 because an unrecovered Go runtime panic exits with status 2 and would be indistinguishable from the usage class.

**Context.** The category value `delivery_unknown` appeared once as an example and was never enumerated; no code-to-exit mapping existed, leaving boundary codes (`path_traversal_rejected`, `quarantine_release_denied`) ambiguous.

**Consequences.** Category and exit code determine each other mechanically. The example error JSON's category changed from `delivery_unknown` to `acceptance_unknown`. `target_response_invalid` is pinned to `acceptance_unknown` per DUR-005.

## D-007 - 2026-08-19 - Error model expresses policy-driven unsafe-path quarantine

**Decision.** The stable error code registry gains `unsafe_path_quarantined` (category `quarantined`, exit 5). A boundary note distinguishes the non-durable containment rejection (`source_unsafe_path`, class 30, used when no safe evidence can be stored) from the durable policy quarantine (class 5), and processing-pipeline disposition rule 1 now names the code for each branch.

**Context.** A multi-agent design audit found that `unsafe_path_action` is a required `const: quarantine` in `config.schema.json` while the closed v0.1 registry had no class-5 code applicable to unsafe paths, so the mandated policy outcome was inexpressible without violating either the schema or the error model.

## D-008 - 2026-08-19 - Follow-up and reconciliation decisions reference generation lineage

**Decision.** `PolicyDecision` gains an optional `generation_lineage { route_id, generation }`; exactly one of `batch_id` or `generation_lineage` is present. Invariant 1 now reads: every decision references either an existing immutable batch or a durable generation lineage. The work completion transaction creates the follow-up policy decision (with generation lineage) in the same commit as the follow-up intent.

**Context.** The invariant required every decision to reference a single immutable batch, but a follow-up covers a dirty generation accumulated across many batches, and scheduled reconciliation has no batch at all. The completion transaction named intent creation but no decision creation, so an implementer had no compliant way to produce a follow-up.

**Consequences.** Audit lineage for follow-ups and reconciliations is explicit, and CON-004 latest-state semantics are preserved: generation lineage identifies why work was requested, not a historical content snapshot.

## D-009 - 2026-08-19 - Route behavior on accepted-then-failed work

**Decision.** The route runtime state machine gains failure transitions: cooperative failure or cancellation with retry budget remaining moves ACTIVE_CLEAN or ACTIVE_DIRTY to FOLLOWUP_READY (one bounded follow-up for latest state, under the same collapse bound as completion); budget exhaustion moves the route to UNCERTAIN for operator resolution. QUARANTINED gains an operator release-or-discard exit edge. `work fail` gains a flag synopsis and a closed v0.1 failure-code set (`agent_error`, `canceled`, `timeout`, `environment_error`), and `work begin` is documented as returning the run ID consumed by `work complete` and `work fail`.

**Context.** The route state machine had no failure transitions, so the changes that activated a route could be silently lost when accepted work failed, contradicting the package's no-silent-loss principle. `work fail` also had no synopsis, and the "stable failure code" requested by the companion skill had no registry.

**Consequences.** FBK-008's "extra bounded follow-up over silent loss" rule now has a defined mechanism on the failure path, and the receipt failure vocabulary is closed like the CLI error registry.

## D-011 - 2026-08-19 - Scheduled reconciliation submits after the production gate

**Decision.** The operations doc now states that pre-gate scheduled reconcile omits `--submit` (audit only) and post-gate recipes add it, matching the CLI contract. Processing-pipeline §7 declares trigger-driven retry liveness intentional for v0.1: due RETRY_WAIT intents are submitted by the next source event or an explicit drain, never by a background timer, and remain visible in `status` and `dispatches list`.

**Consequences.** Operators get a correct post-gate recipe, and the trigger-driven tradeoff is now an explicit design position rather than an accidental gap.

## D-013 - 2026-08-19 - Route failure budget is an explicit field

**Decision.** Route dispatch configuration gains `failure_budget` (integer, 1 through 10, required): the maximum number of consecutive failed or canceled accepted tasks before the route moves to `UNCERTAIN`. A completed task resets the count. The failure-path references in the persistence state-machine note, feedback-loop §7, and the `work fail` contract now cite `failure_budget` instead of reusing `execution_hints.max_attempts`.

**Context.** D-009 bound the route's consecutive-failure budget to the Hermes execution hint, giving one field two meanings that can diverge: the hint advises the runtime about execution retries inside Hermes, while the budget governs how many follow-up intents Agent Dispatch creates after accepted work fails.

**Consequences.** The three budgets are now distinct and documented together in `configuration-spec.md` §9: `submission_retry.max_attempts` (delivery attempts for one intent), `execution_hints.max_attempts` (Hermes execution hint), and `failure_budget` (consecutive accepted-work failures). `failure_budget` is behavior-affecting and participates in the route revision digest. Config schema, both config examples, the domain-model Route, and the revision-input list are updated.

## D-015 - 2026-08-20 - E1-T1 owns the Makefile verification entrypoint, the Go schema validator, and gaori retargeting

**Decision.** E1-T1 introduces the Makefile as the single deterministic verification entrypoint, with explicit targets for the package checks (manifest checksums, schema/example validation, traceability regeneration). Schema and example validation moves to a Go implementation using a standard Draft 2020-12 validator (for example `santhosh-tekuri/jsonschema`), replacing `docs/scripts/validate-json-schemas.py`; its self-test cases are migrated to Go unit tests. `.gaori/tester.yaml` commands are re-targeted from raw `bash -c` argv to the Makefile targets, so gaori evidence capture tracks the entrypoint instead of duplicated command text. **Context.** The E0 audit remediation left a stdlib-only Python subset validator with accepted deferrals (subset-enumeration duplication, no static `$ref` target resolution, only the `date-time` and `uri` formats). The gaori configuration added during the E0 closeout wraps raw commands, which would silently drift from the documented verification commands once those become Makefile targets.

**Consequences.** The Python dependency for document validation disappears at E1-T1, discharging the deferred standard-validator items in `VALIDATION.md`. Until E1-T1 completes, the current Python commands and gaori configuration remain the authoritative reproduction path.

## D-016 - 2026-08-20 - Usage-class error codes registered for the E1-T1 CLI surface

**Decision.** The closed v0.1 error-code registry gains its first usage-class (exit 2) codes: `command_unknown` for an unrecognized command, `command_not_implemented` for a command defined by the CLI contract but not yet built, and `flag_invalid` for argument errors. `internal_unclassified` (exit 40) gives the required panic-recovery path a legal code. The minimal E1-T1 CLI emits only these four codes plus success; the registry stays closed and future codes remain contract changes recorded here and in the changelog.

**Context.** The registry predated any executable CLI and contained no usage-class codes, so the first real `agent-dispatch` binary had no legal encoding for its failure modes; emitting unregistered codes would violate error-model §4 ("implementations emit only the codes below").

**Consequences.** SOT 1.0.4. `version` and `init` are the first implemented commands (init landed with E1-T2); every other tree entry fails closed with `command_not_implemented` instead of silently succeeding.
