# v0.1.6 Operational Reliability Follow-up

> **Status:** Approved planned baseline
> **Decision:** D-027
> **Release target:** v0.1.6
> **Shipped baseline:** v0.1.5
> **Roadmap owners:** E14 through E17

## 1. Purpose

This specification adopts the focused follow-up discovered while deploying
Agent Dispatch v0.1.5 against Hermes Agent v0.20.5 on macOS/arm64. The release
closes exactly three operational gaps:

1. guided Wiki setup must select and preserve one route and be safely rerunnable;
2. Hermes without `--mutex-key` must remain compatible under an explicit local
   serialization guarantee;
3. durable notification work must make bounded progress without a remembered
   manual drain command.

The separately requested general `make verify` remediation is not part of this
release. Hermes core, private state, plugins, versions, and tags remain outside
Agent Dispatch authority.

## 2. Guided Setup Contract

`setup wiki` accepts `--route <id>`. A one-route configuration may select its
only route automatically. A configuration with multiple routes must use the
flag or an interactive, clearly rendered choice; non-interactive execution
without a choice fails. Every route-scoped nested command, printed Watchman
command, baseline operation, and final enable command uses that exact route ID.

The setup baseline is the public command:

```text
agent-dispatch reconcile --route <id> --reason initial --baseline-only
```

Baseline-only reconciliation is permitted only when configuration and runtime
activation are disabled. It enumerates the bounded resource snapshot and
atomically records the snapshot plus a route baseline record. It creates no
policy decision, dispatch intent, Hermes task, completion notification, or
production acknowledgement. It cannot submit and cannot be used to resolve an
active, uncertain, quarantined, or production-enabled route. A crash leaves
either the previous baseline or the complete new baseline; rerunning converges
without duplicate work.

The final setup summary reports separately:

- configuration enabled state;
- runtime activation state;
- Watchman binding state;
- initial baseline state;
- production acknowledgement state.

It prints the exact reviewed `route enable` command and never executes it.

## 3. Hermes Mutex Compatibility and Serialization

`--mutex-key` is optional capability evidence. A Hermes target missing only
that flag remains compatible when Agent Dispatch can enforce the configured
serialization topology. Probe, capabilities, preflight, enablement, rendering,
submit-time executable revalidation, and status use one of these effective
modes:

- `target-enforced`;
- `agent-dispatch-group-enforced`;
- `unsupported-unsafe`.

Every destination has an effective Agent Dispatch serialization group. The
planned resolution order is explicit `serialization_group`, existing
`mutex_key`, then a route/destination-derived private group. A group is global
within one Agent Dispatch SQLite state database. At most one active child may
hold it. New relevant work for an occupied group merges into the selected
destination lane's dirty generation. Completion promotes at most one waiting
lane; retry retains the slot and rerun transfers it atomically. Independent
groups may run concurrently.

Destinations governing the same resource but using different groups fail
preflight unless every involved route records the behavior-affecting
route-level acknowledgement that cross-group concurrency is permitted. This
acknowledgement and each effective group participate in destination and route
revision. Agent Dispatch never claims global single-writer safety across
different state databases.

When target mutex support is absent the renderer never emits `--mutex-key`.
When support exists, the target key may complement but never replace the local
group slot. Hermes 0.19.1 remains supported wherever its public shapes still
match; Hermes 0.20.5 is explicitly certified for the mutex-only downgrade.

## 4. Automatic Notification Drain Contract

The planned per-route configuration is:

```yaml
notifications:
  events: []
  sinks:
    - id: ops-log
      type: log
  drain:
    mode: after-command
    limit: 100
    failure_policy: preserve-pending
    pending_warn_after: 1h
```

An omitted drain block on an existing v0.1.5 configuration means `manual`.
Newly generated Wiki configuration uses `after-command`. Supported modes are:

- `manual`: only an explicit notification drain delivers pending records;
- `after-command`: one route-scoped bounded pass runs after a successful
  notification-producing state transition commits;
- `scheduled`: ordinary commands do not auto-drain and a generated launchd
  recipe chains drain after a healthy scheduled reconciliation.

Automatic delivery is never part of the source transaction. Failure cannot
roll back or relabel source state, change successful command exit status,
resubmit work, or create a recursive notification about a successful drain.
Ambiguous and retryable outcomes remain pending under the original stable
idempotency identity; refused delivery remains inspectable and explicitly
retryable. Concurrent drainers atomically lease disjoint work. A crash after
source commit or after remote delivery leaves recoverable at-least-once work.

`schedule render --route <id> --platform launchd` resolves the actual binary
and configuration paths, uses explicit bounded log paths, runs scheduled
reconciliation with `--submit`, and runs notification drain only after a zero
reconciliation exit. Its output includes install, inspect, disable, and
uninstall instructions. Uninstall preserves configuration and SQLite state.

Status and doctor expose pending count and age, the latest drain evidence,
mode and limit, scheduler expectation/evidence/overdue state, repeated
ambiguous or retryable outcomes, and unresolvable sinks. No notification
payload or diagnostic may include document bodies, front matter, secrets, or
an unredacted endpoint.

## 5. Compatibility, Migration, and Rollback

Configuration remains `version: 1` with additive fields and explicit effective
defaults. Behavior-affecting fields join the appropriate route, destination,
or notification-policy revision without changing existing notification
identity. Capability evidence advances to a new probe-contract version and old
evidence becomes stale with a re-probe remediation.

SQLite migrations are forward-only. Existing dispatch, receipt, lane, and
notification identities remain unchanged. Upgrade instructions require a
verified pre-migration backup, capability re-probe, preflight, and explicit
production re-acknowledgement where a serialization revision changed.
Downgrade restores the pre-upgrade database, previous binary, and compatible
configuration together; no down migration is provided.

## 6. Required Delivery Evidence

E17 cannot release v0.1.6 until the repository records:

1. concise design and changed-contract summaries;
2. exact migration and CLI/config examples;
3. acceptance-test mapping and focused command results;
4. clean-host setup and post-Watchman-install rerun transcripts;
5. real Hermes v0.20.5 probe and preflight evidence;
6. shared-group and independent-group concurrency demonstrations;
7. completion, outbox commit, automatic delivery, and timeout retry evidence;
8. known limitations plus upgrade and rollback instructions;
9. full repository verification and two reproducible darwin/arm64 builds.

All real-environment evidence uses disposable state, vaults, boards, and
profiles. No production route is enabled and no production Hermes task is
created by the validation setup flow.
